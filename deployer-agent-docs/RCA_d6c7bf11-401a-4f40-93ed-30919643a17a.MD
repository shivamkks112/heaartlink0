## Answers to the 4 questions

### (1) Replicas / pods and uvicorn workers — ROOT CAUSE
- **Pods/replicas:** tier_0 "Starter" runs **`replicas: 2` (max_replicas 2, HPA disabled)** → **2 backend pods** always serving.
- **uvicorn workers per pod:** entrypoint.sh starts `uvicorn server:app --host 0.0.0.0 --port 8001` with **no `--workers` flag → 1 worker (1 process) per pod.**
- **Net:** 2 pods × 1 worker = **2 independent Python processes**, each with its **own in-memory ConnectionManager**.
- This is the core break, exactly as suspected: a client's WebSocket `/api/ws/{user_id}` is pinned to **one** pod, while the sender's `POST /api/messages` can land on **either** pod (Cloudflare → k8s Service round-robins). When the save-pod ≠ the pod holding the recipient's (or sender's) socket, the in-process `manager.send(...)` finds no local socket and the real-time echo/delivery is silently dropped. **FCM push still arrives because it is an external HTTP call, independent of the in-process socket registry** — this is why push works but the live socket echo does not.

### Ingress WebSocket idle timeout
- Not directly readable with the available tools. This app's frontend is **Cloudflare** proxying WS to the k8s backend; Cloudflare-proxied WebSockets have a **~100s idle timeout by default** (inferred, not verified here). Without a server-side ping/keepalive under that interval, idle sockets get cut — which compounds the reconnect storm seen in the logs.

## Root cause (proven)
**Primary:** The WebSocket `ConnectionManager` is **in-process memory**, but the app runs **2 pods × 1 uvicorn worker**. Message writes and recipient sockets are not guaranteed to be on the same process, so real-time cross-user delivery (and the sender's own echo) is dropped whenever they diverge. FCM push is unaffected because it is external. (Proven by tier config `replicas:2`, entrypoint single-uvicorn, and the symptom pattern.)

**Contributing:** Backend pod churn + 503 liveness/readiness/startup failures at 05:41–05:54 UTC (just before the reported sends) tore down/reconnected WS sessions. At tier_0 the backend request is **CPU 50m (limit 250m) / mem 200Mi (512Mi)**; the startup "connection refused" + 503 timing is consistent with CPU-starved slow boots/handlers, though a direct throttle metric was not captured. Separately, recurring **500s + ASGI tracebacks** on `/api/active-users` and `/api/discover` indicate a latent route bug whose final exception line was not captured.

## Suggested fixes
1. **(Code / E1)** Replace the in-memory `ConnectionManager` with a **cross-pod delivery mechanism** — Redis pub/sub or Mongo change-streams fan-out — so a message saved on any pod is pushed to the recipient's socket wherever it lives. Add a **server-side WS ping/keepalive < ~90s** to survive the Cloudflare idle timeout. Also triage the 500s on `/api/active-users` & `/api/discover` (capture the final exception behind the BaseHTTPMiddleware exception-group). *(Not reproduced in sandbox — this is a multi-pod/live-DB behavior the eph pod cannot reproduce.)*
2. **(User — Resources tab)** Consider a higher tier: at tier_0 the pods flapped and returned 503 on health probes in the exact window, which drops WS sessions. More CPU headroom reduces boot/handler stalls and churn. (Contributing reliability factor; attribution inferred from probe-failure timing, not a direct throttle metric. Note: the cross-pod bug in fix #1 remains even with 1 pod unavailable / more pods — it must be fixed in code regardless.)
