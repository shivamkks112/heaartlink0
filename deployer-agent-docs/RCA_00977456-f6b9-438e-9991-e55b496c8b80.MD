# RCA — HeartLink (www.heartlink.co.in): "Failed to load profile" toast

## Problem statement
Users intermittently see toast "Failed to load profile". Frontend calls `GET /api/profile/{user_id}` (ProfilePage) and `GET /api/profile/{id}?slim=1` (UserProfilePage). Works in preview, fails in production. Suspected cause named by reporter: recent backend change adding `"premium_pass_until": 1` to Mongo inclusion projections and `helpers.is_user_premium` now reading `premium_pass_until`.

## Verdict
**The failures are caused by intermittent MongoDB Atlas transport-level timeouts, NOT the `premium_pass_until` code change.** Active run: `00977456-f6b9-438e-9991-e55b496c8b80` (success, currently serving).

Also observed:

These Mongo exceptions propagate up through Starlette's `BaseHTTPMiddleware` stack (outer middleware `block_suspicious_requests` at `server.py:9462`), which converts an unhandled exception into:
```
  | ExceptionGroup: unhandled errors in a TaskGroup (1 sub-exception)

```
→ returned to the client as **HTTP 500** → frontend shows "Failed to load profile". Confirmed 500s on DB-backed routes e.g. `GET /api/discover/... 500 Internal Server Error`.

### 2. Profile endpoints themselves are fine — failures are intermittent
Recent log sample shows `GET /api/profile/{id}` and `?slim` variants returning **200 OK**. The toast appears only during Atlas timeout bursts, which hit every DB-backed endpoint simultaneously (profile, discover, background "online status cleanup" also timed out). Nothing specific to the profile route.

### 3. Pod health / memory
- `get_pod_events`: Liveness/Readiness/Startup probes failing with **503**, and nginx logs `upstream timed out (110) while reading response header from upstream GET /health`. The `/health` handler does `await client.admin.command('ping')`; when Atlas is unresponsive the ping hangs and `/health` times out → probes flap pods to NotReady.
- **No OOMKilled, no evictions, restart_count = 0** → memory is NOT the problem (tier mem limit 512Mi). This is a DB-connectivity + event-loop-saturation issue, not memory.

### 4. The premium_pass_until change is ruled out
- `services/helpers.py:132 is_user_premium(user: dict)` operates on an **already-fetched dict** — it performs **no database I/O**, so it cannot cause Mongo timeouts.
- `mongo_query` on `users` (1489 docs): **0 documents** have `premium_pass_until` set (`$exists:true,$ne:null` → 0; `$type:date` → 0; `$type:int` → 0). So the `"" > isoformat()` string-comparison path is never exercised with a non-string, and there is **no `TypeError` in logs** (searched explicitly).
- `"premium_pass_until": 1` in projections is a MongoDB inclusion flag (include field), not a data value — harmless.
- NOTE (latent, not currently firing): `is_user_premium` compares `user.get("premium_pass_until", "") > datetime.now(timezone.utc).isoformat()`. If a future write ever stores `premium_pass_until` as a BSON date / int (e.g. the literal `1`), this `>` will raise `TypeError: '>' not supported between instances of ...` and 500. Recommend making it type-safe. Not the current outage cause.

### 5. Client config that makes the app fragile to Atlas latency (`backend/database.py`)
```python
client = AsyncIOMotorClient(
    mongo_url,
    maxPoolSize=100, minPoolSize=20, maxIdleTimeMS=60000,
    connectTimeoutMS=3000, serverSelectionTimeoutMS=3000,
    retryWrites=True, retryReads=True, compressors="zstd,snappy,zlib",
)
```
`connectTimeoutMS=3000` / `serverSelectionTimeoutMS=3000` are aggressive — any Atlas latency/connection-setup blip > 3s surfaces immediately as `NetworkTimeout`. No `socketTimeoutMS` is set. Backend runs a **single uvicorn worker** (`entrypoint.sh`: `uvicorn server:app --host 0.0.0.0 --port 8001`, no `--workers`) on **tier_0 (cpu_limit 250m)** × 2 replicas; when Mongo ops stall, the one event loop saturates and `/health` can't be served → probe flaps compound the outage.

## Root cause
Production MongoDB Atlas (shard node `customer-apps-shard-00-01.sy89cj.mongodb.net`) is intermittently slow/unreachable — read operations and TLS handshakes exceed the client's 3s timeouts, raising `pymongo.errors.NetworkTimeout`. These unhandled exceptions become HTTP 500s on DB-backed endpoints (including `/api/profile/*`), producing the "Failed to load profile" toast, and also hang `/health` causing probe 503 flaps. This is an Atlas-side capacity/connectivity problem, made fragile by the app's aggressive Mongo timeouts and single-worker/tier_0 CPU. It is unrelated to the `premium_pass_until` change.

## Fixes
1. **MongoDB Atlas (third-party, primary)** — Inspect the production Atlas cluster's health/metrics (connections, CPU, IOPS, slow queries) for `customer-apps-shard-00-01`. The read + SSL-handshake timeouts point at Atlas-side saturation/instability. If on a shared/undersized cluster, upgrade the Atlas cluster tier. Only the account owner can do this in Atlas.
2. **Code resilience (E1, UNVERIFIED — cannot be reproduced in the sandbox since it has no live DB/secrets):** In `backend/database.py` raise `connectTimeoutMS`/`serverSelectionTimeoutMS` (e.g. 10000–20000ms), add an explicit `socketTimeoutMS`, and consider lowering `minPoolSize`. Also wrap DB-backed handlers / add middleware to return a graceful 503 instead of a bare 500 on `NetworkTimeout`. Separately, make `is_user_premium` type-safe against a non-string `premium_pass_until` (latent bug).
3. **Tier (optional, contributing):** tier_0 gives 250m CPU with a single uvicorn worker; the event-loop saturation during Mongo stalls worsens the `/health` probe flapping. More CPU headroom would reduce the cascade, but it is a contributor, not the primary cause (Atlas is).
